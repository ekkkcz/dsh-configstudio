> **本轮的流程教训（值得记）**：改名是**机械替换**，它分不清"当前的产品名"与
> "**历史交付物当时叫什么**"。凡是脚本里既有"现在的名字"又有"老版本的东西"，
> 替换就会造出**不可能成立的期望** —— 而且长得跟产品缺陷一模一样（5/7 失败）。
> 判据：**遇到老版本产物，名字要从那个产物自己读出来，不能在源码里写死。**

同一道题 → 两个候选各自一次**真实**模型调用 → 原始正文与提取出的 HTML 分别落盘 →

### 关键决定（含理由）

| 决定 | 理由 |
| --- | --- |
| 形态：外部 cordis bundle，宿主半边 + 浏览器半边 | DSH 官方支持这条路径，且本机已有可用实例（dsh-prompt-optimizer）作为参照 |
| 整页用自己路由吐的静态 SPA，DSH 侧只挂一个 iframe 入口 | 外部包没有官方前端构建链，平台模块表白名单冻结。这样 DSH 侧耦合最小 |
| 浏览器半边只 `require('react')`，只 `inject: ['slots']` | `dsh.client.inject` 只保证工厂到达顺序，不保证 `require` 可用 |
| 模型调用用 `ctx.get('llm')` 而非 `ctx.llm` | 直接读会在真实 DSH 里抛错（实测 500）；且 llm 是可选能力 |
| 存储用 `node:sqlite`（Node 内置） | 零原生编译依赖，Windows 上开箱可用（已实测） |
| 预览承载：独立端口服务 + iframe sandbox + 响应头 CSP + postMessage 校验 | 四层组合；不把不同端口当成 cookie 隔离，也不开放 `allow-same-origin` |
| 截图用独立浏览器进程（可硬杀） | F14 要求"独立可终止"，不能只靠同线程超时回调 |
| **M1**：盲选脱敏要在"作品卡头部"和"配置差异折叠面板"两处都做 | 折叠面板只是折叠，点一下就能看见（实测缺陷） |
| **M1**：保存评价后只做最小刷新，不重绘作品区 | 重绘会重建 iframe，把用户在作品里的操作状态全部丢掉 |
| **M1**：揭晓后作品卡直接写出 provider / model | 候选默认名就是 A / B，只显示名字等于没揭晓（实测缺陷） |

**为什么第二个候选换成了 `deepseek/deepseek-v4-pro`**：交接建议的
`xkiro/deepseek/deepseek-v4-pro` 在模型目录里存在，但上游返回

## 当前错误与已知限制

### M1 实测暴露并已修复的缺陷（4 个）

1. **保存评价后"揭晓身份"按钮不出现**，盲选流程走不下去。
   原因：`saveVote()` 更新了 `state.current.vote`，但揭晓按钮的显隐只在 `renderCompare()` 里算，
   保存评价不触发重绘。修法：抽出 `updateIdentityControls()`，保存评价后调用它
   （**刻意不整页重绘**——重绘会重建 iframe，丢掉用户在作品里的操作状态）。
2. **隐藏配置身份期间，折叠的"配置差异"面板仍写出 provider / model**。
   原因：`renderCompareDetails()` 不读 `state.blind`。折叠只是折叠，点一下就能看见。
   修法：`state.blind && !state.revealed` 时把模型来源 / 模型 / 候选名渲染成"（已隐藏，揭晓后可见）"。
3. **揭晓后作品卡仍只写 A / B**：候选默认名就是 "A"/"B"，用户看不出谁是谁，还得去翻折叠面板。
   修法：非隐藏状态下卡片头部直接显示 `候选名 · provider / model`。
4. **开发服务器 `/models` 与 `/models/resolve` 返回 500**：`runtime.llmOf is not a function`。
   原因：`api.js` 用 `runtime.llmOf()` 取模型服务，而 `scripts/dev-server.mjs` 自己拼的 runtime 漏了这个字段。
   **M0 的演练之所以一直是绿的，是因为当时那个开发服务器进程跑的是改动前的旧代码**；进程一重启就暴露。
   修法：给开发服务器 runtime 补 `llmOf: () => llm`。

第 1–3 个只在真实浏览器里点得出来，node 单测与模拟演练都覆盖不到；第 4 个说明"长期不重启的开发进程"
会让演练结果失真，已记入环境注意事项。

### 第二轮反馈期间修复的缺陷（5 个）

1. **重绘把用户展开的 `<details>` 收回**（用户第 2 条反馈，真缺陷）。
   根因：`startRunPolling()` 每 700ms 调 `renderRun()`，而后者开头就是 `clear(box)`。

   修法：`renderRun()` 改 keyed 增量更新（详见附二·反馈 2）。用新写的模拟模型

### 环境注意事项（给后续接手者）

- **PowerShell 控制台会显示中文乱码**（例如 `Get-Content` 的输出看起来像乱码），
  但文件本身是正确的 UTF-8。判断文件内容请用 `read` 工具或设置
  `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`，不要被控制台显示误导。
- 通过 PowerShell 向 node 传中文参数会被转成 `?`（踩过一次，产生了一条标题为 `???????` 的
  测试实验记录）。需要传中文时请写成 .mjs 脚本文件再执行。
- 本机装有两份 playwright（DSH checkout 内 1.61.1 与全局 @playwright/cli 内的 1.63）。
  **只有 1.63 对应的浏览器修订号在本机存在**，插件已实现"逐个候选尝试启动"，
  所以两份都在也能正常工作。
- **端口可能被别的程序占用**：本轮实测 **8901 被本机另一个与本插件无关的程序监听**，
  导致 DSH 测试实例起不来（表现为"端口在监听但连不上"，因为占着端口的是别的程序）。
  排查方式：`Get-NetTCPConnection -State Listen -LocalPort 8901` 看 `OwningProcess` 是谁。
  **交接文档里不要写死端口号** —— 本轮就因为这个把回归清单里的 8901 抄成了过期命令，
  接手者照抄会直接 `ERR_CONNECTION_RESET`（已实测复现）。正确做法是让接手者先核对实际端口。
  **不要为了让 DSH 起来去结束用户的程序**，换个空闲端口即可（本轮改用 **8902**）。
- **后台作业会随工具调用被中断一起消失**（DSH 实例与开发服务器都会被带走）。

- **不要相信一个长期不重启的开发服务器进程**：M0 的界面演练曾在旧代码上一直是绿的
  （见"已修复缺陷"第 4 条）。改了 `src/` 下任何非界面文件后，务必重启开发服务器。
  `web/` 下的界面资源是按 mtime 重读的，改界面不用重启。

  导致某些缺陷只能在真实 DSH 上复现。**新增这类共用逻辑时请加在 `core/runtime.js`**，

- **`scripts/simulated-llm.mjs` 增加了 `sim-reasoning`**（会先流式输出推理再输出正文）。

### 3.1 修掉的缺陷

1. **实时生成监控是死代码**（用户第 3 条）。`runGeneration` 一直在发 `text-delta` / `reasoning-delta`，
   但宿主的 `runCandidate` 只取了两个时间戳，**把正文片段整个丢掉**；
   界面 `state.streams` 只被清空和读取，从未被写入。所以那段"正文流"永远是空的。
   修法：宿主侧加 `this.live` 缓冲（每候选保留尾部 64KB，只用于观察、不作权威数据），
   新增 `GET /experiments/:id/live`，界面 700ms 轮询并自动吸底。
   实测：一次生成中连续采样得到 `0 → 400 → 1892 → 2860 → 3141`，确实在长。
2. **四候选对比挤成一条**（用户第 4 条）。`.compare-grid` 写死 `1fr 1fr`，
   4 个作品会排成一行四列，每个都窄到看不清。修法：`shown.length >= 3` 时加 `multi` 类，
   走两行两列、窄屏退化为单列。实测四候选布局 `(50,155) (806,155) (50,634) (806,634)`，同行等宽。

### 3.2 新增能力

- **输出要求预设**：7 条常用要求（无依赖单 HTML、响应式、不用框架、内置数据、
  必须有交互、可访问性、不写占位）。纯静态清单，`GET /requirement-presets`。
  点一下把文字**追加**到输出要求框，再点移除，**不覆盖**手写内容。
- **提示词优化器对接**（`src/core/optimizer.js`）：见专门文档 `docs/optimizer-integration.md`。
  要点：对方**没有 provide 服务、没有导出函数**，唯一入口是它自己的 HTTP API；
  我们与它同进程同端口，用请求的 `Host` 直接回到本机，**不需要用户配端口**；
  一律 **fail-open**（不可用就隐藏该功能，不影响主流程）；优化结果**先给用户看**，
  点"替换 / 追加 / 丢弃"才生效。
- **"再添加一个"按钮**：自动挑一个当前没用过的模型，省掉 3–4 套配置时的重复下拉。

### 反馈 2：展开的 details 被轮询自动收回（**已修**）

**现象**：运行面板里点开"推理过程"，不到 1 秒就自己收回去。

**根因**：运行面板的轮询（`startRunPolling`）每 700ms 调用 `renderRun()`，
而 `renderRun()` 每次都用 `clear(box)` **把整个候选区 DOM 全部重建**。
于是用户展开的 `<details>` 在下一个轮询周期就被换成全新的、默认收起的节点。

**已用探针实测确认**（`scripts/m2-redraw-probe.mjs`，零模型费用）：
往运行面板的候选卡上打 `data-probe` 标记并展开一个 `<details>`，等 1.6 秒（跨两轮轮询）后再找：

```text
{ before: { cards: 2, marked: true, open: true },
  after:  { cards: 2, markerSurvived: false, probeDetailsExists: false },
  verdict: '节点每轮被重建（details 的展开状态必然丢失）' }
```

**影响范围不止推理过程**（同一根因导致的一类问题，修复时一起处理）：
- 用户展开的**任何** `<details>` 都会被关掉（包括"原始输出与提取结果"、实时流里的推理过程）。
- 实时输出区的**滚动位置**每轮丢失（现在靠每轮重新 `scrollTop = scrollHeight` 掩盖了）。
- 如果用户正在面板里选中文字，会被打断。

**实际修法（已实现）**：采纳第 1 个方向 —— `renderRun()` 改为 **keyed 增量更新**：

- 卡片骨架只在**候选集合**（attempt id 列表）变化时重建，其余时候节点一直复用；
- 文本一律走 `setText()` **原地改写文本节点的值**，不重建子树（选区、滚动位置都挂在节点上）；
- 实时输出只在"用户本来就贴着底部"时才自动吸底，向上翻阅时不抢滚动条。

**修这个缺陷时暴露的一个更大的问题（值得记下来）**：
开发服务器 `scripts/dev-server.mjs` 里手抄了一份 `runCandidate`，和 `src/index.js` 漂移了 ——
宿主半边有实时流缓冲（`/live`），开发服务器**没有**。后果是：这个缺陷在真实 DSH 上会出现，
但在**零费用的开发服务器上根本复现不出来**，而后者正是我们做界面迭代的地方。
已抽出 `src/core/runtime.js`，宿主半边与开发服务器**共用同一份实现**（`createRunCandidate` /
`liveFor` / `LIVE_MAX`），并在开发服务器启动横幅上打印实时流状态，避免再出现"两边跑的不是同一份逻辑"。

**审查子代理发现的同类缺陷（同一"重绘丢用户状态"根因），一并修掉**：

| 缺陷 | 现象 | 修法 |
| --- | --- | --- |
| `takeScreenshots()` 每张截图完成就调 `renderCompare()` | 4 候选 = 4 次 `clear(compare-grid)` + 重建 iframe；**用户在作品里的操作被重置 4 次** | 截图面板拆到独立的 `#screenshot-panel`，只重画截图区，**不碰作品网格** |
| `buildFrame()` 每次重绘都 `addEventListener('resize')`，从不移除 | 每次重绘累积监听器，闭包捕获已脱离 DOM 的节点 | 重绘前统一摘掉上一轮的处理器（`window.__arenaResizeHandlers`） |
| `saveVote()` 不回填 tags / note | 保存后刷新页面，标签与理由**变空**（服务端其实存了） | 用服务端返回值回填 checkbox 与文本框 |
| 搜索框每次按键发请求、无序号 | 响应乱序时列表被旧结果覆盖 | 加序列号守卫 + 180ms 防抖 |
| 对比页运行时错误每次都改写同一文本节点 | 作品报错会把下方内容下推、打断选中 | 内容未变就不写；只原地更新独立节点 |

**修复方向**（保留当时的判断，供对照）：1 是根治（已采纳），2 只是让全量重建立刻不明显。

### 反馈 3：中途输入提示词（**已实现：方案 1 追加轮次**）

**用户的期望**：生成过程中还能继续输入提示词；中途输入时也能选择过一遍插件。

**与现有规定的冲突**：PRD **F02 明确"单候选使用单次逻辑生成请求，不开启工具执行"**，
而且 `docs/dsh-integration.md` 第 2.3 节确认：插件直调 `ctx.llm.stream()` **不会被重试**，
所以本插件一直把"逻辑请求数 = 网络请求数"当作可核对的性质（`observedRequests: 1`）。
"中途往同一次请求里再塞提示词"在**流式接口上做不到**（请求已经发出、消息已冻结），
硬做只能变成多次请求，那就必须如实记录成多次，不能继续声称单次。

**可选设计（需要用户拍板取哪个）**：
1. **追加轮次**（推荐）：把中途输入作为**新的一轮 attempt**（复用已有的"重试新建 attempt"机制，
   原 attempt 与其原始输出完整保留）。界面明确写"这是第 N 轮，第 1 轮的原始输出仍可下载"。
   好处：不破坏 F02 与可核对性；坏处：不是"插进当前流"。
2. **仅发送前注入**：只在"第一个 token 到达之前"允许改提示词（超过就禁止并说明原因）。
   最保守，但用户体验上接近"不能中途输入"。
3. **有意的多轮对话**：把 F02 改写成"每轮单次请求"，明确记录轮次与每轮的请求数。

### 反馈 1：要能水平展开比对（**根因已实测定位**）

**用户的截图看着像"上下堆叠"**（两张卡片一上一下），而我在 1983px 宽度下量到的是**并排**。
已用 `scripts/m2-layout-probe.mjs`（本轮新增，零费用只读）扫描宽度，实测断点如下：

| CSS 视口宽度 | 布局 |
| --- | --- |
| 1983 / 1600 / 1400 / 1200 / 1100 / 1000 / 950 px | **左右并排**（每卡 744 / 676 / 576 / 526 / 476 / 451 px） |
| **900 / 880 / 700 px** | **上下堆叠**（单列 864 / 844 / 664 px） |

**根因就是 CSS 的这条媒体查询**（`web/app.css`）：

```css
@media (max-width: 900px) { .compare-grid { grid-template-columns: 1fr; } }   /* app.css:245-246 */
```

用户截图是 **1983 物理像素**，但若 DPR ≈ 2.25（高 DPI 屏或浏览器缩放），
**CSS 视口就只有约 880px** → 命中 `≤900px` → 堆叠。**所以这不是"用户不会用"，是真实布局问题**：
在窄视口下插件直接把并排比对关掉了，而"并排比对"正是这个产品的核心动作。

**用户要的"水平展开比对"应该包含两件事**（实现时按此确认，不要只做一半）：
1. **强制并排**：即使视口窄，也要能把两个作品左右摆在一起看（而不是自动改成上下）；
2. **窄视口下的可读性**：并排后每卡只有 ~400px，需要能**横向滚动**看完整宽度，
   或者提供"同步滚动"让左右跟着一起滚 —— 否则并排了也看不全。

**注意既有约束**：`.compare-grid` 的列数由 `renderCompare()` 里的
`shown.length >= 3 ? ' multi' : ''` 与 `single` 类共同决定；**全屏**按钮
（`fullscreen()`）会写 `compare-grid single` 类。改这里要一起看这三处，
别让"全屏"和"强制并排"互相打架。

### 反馈 2：最终页面要显示 token 消耗、速度等数据（**数据全在，只是藏得深**）

**现状**：这些数字**已经在**对比页的「展开配置」面板里（v0.3.0 刚加的），
但它**默认折叠**，用户看不到 —— 这正是他提这条的原因。

**实测拿到每个候选可用字段**（用用户那条真实实验量出来的，`m2-layout-probe.mjs`）：

| 字段 | 来源 | 示例（用户实验） |
| --- | --- | --- |
| `inputTokens` / `outputTokens` / `totalTokens` | `receipt.usage` | 750 / 41234 / 41984 |
| `cacheReadTokens` / `reasoningTokens` | `receipt.usage`（可能为 null） | 0 / **null** |
| 总耗时 | `finishedAt - startedAt` | 179415 ms |
| **首正文延迟** | `firstTextAt - startedAt` | **168281 ms** |
| 首正文→结束 | `finishedAt - firstTextAt` | 11134 ms |

**⚠️ 速度口径必须想清楚，别直接算 `outputTokens / (finishedAt - firstTextAt)`**：

那条算出来是 **3703 tok/s**（明显失真）—— 因为**推理型模型先把大量 reasoning token 吐完才出正文**，
`outputTokens` 含推理 token，而分母只算了"出正文之后"的时间。
用户这条实验里**光是等首正文就等了 168 秒**。

建议界面按这两个口径分别显示，并写清含义：
- **总速度** = `outputTokens / (finishedAt - startedAt)` → 229.8 tok/s（对用户更有意义）
- **首正文延迟** = `firstTextAt - startedAt` → 168.3 秒（推理模型的主要等待）

### 反馈 1：水平展开比对

**根因确认（上一轮已定位，本轮复现→修复→复验）**：`web/app.css` 里那条
`@media (max-width: 900px) { .compare-grid { grid-template-columns: 1fr } }`。
用户截图是 1983 物理像素，但他那块屏 DPR ≈ 2.25 → **CSS 视口只有约 880px** → 命中该断点。
复验用 `--deviceScaleFactor 2.25` + 880 CSS 像素**真实复现了他的场景**（见下表）。

**修法（三处一起改，缺一处就会互相打架）**：

| 处 | 旧行为 | 新行为 |
| --- | --- | --- |
| `renderCompare()` | `grid.className = 'compare-grid' + (<=1 ? ' single') + (>=3 ? ' multi')`，列数交给 CSS | **行内写死** `gridTemplateColumns = repeat(N, minmax(0,1fr))`，N = 1 或 2；CSS 那条断点已删除 |
| 读法 | 只有"缩放到能看全" | 新增「缩小看全 / **1:1 横向展开**」+「左右同步滚动」两个开关（故意分开：一个管多宽、一个管跟不跟） |
| `fullscreen()` | 把 grid 类改成 `compare-grid single`（= 单列，与"始终并排"冲突） | 只隐藏别的卡片 + 让这张跨满整行（`grid-column: 1/-1`），**列数不变**；卡头双击也能放大/恢复 |

**1:1 横向展开的实现要点**：作品按 1280px **原始宽度**摆在等分的卡片里，
**每张卡片各自横向可拖**（`.scaler` 从 `overflow:hidden` 改为 `auto`），
拖动时其余卡片按**同一比例**跟随 —— 按比例而不是抄 `scrollLeft`，因为网格与卡片容器的
可滚距离并不相等（网格还要减掉卡片间距与内边距），抄像素会让左右画面错开。

**切换模式不重建 iframe**：`applyCompareMode()` 只改缩放与滚动属性，重绘时用
`rememberScroll()` / `restoreFrameScroll()` 把横滚位置按比例放回 ——
这个项目已经因为重绘吃过两次亏（推理过程被收回、截图重置作品），不再交第三次学费。

**顺带修掉的一个旧问题**：`refitFrames()` 取代了"每次 buildFrame 挂一个 window resize 监听"。
旧办法既没解决"切视口/换模式后作品不重新适配"，又会在重绘时累积监听器、闭包捕获已脱离 DOM 的节点。
现在按 DOM 现场重建，只认还在文档里的节点。

### 反馈 2：最终页面显示 token / 速度

**现状**：数据服务端一直都有，v0.3.0 也渲染了，但只在**默认折叠**的「展开配置」里 = 用户看不见。

**现在**：每个作品卡**头部正下方**一条用量摘要（`data-attempt` 定位，与卡片同生命周期）：
输入 / 输出 / 合计 / 推理 tokens、**总速度**、**首正文延迟**、**总耗时**。

**★ 速度口径（本版最容易做错的地方）**：

| 口径 | 公式 | 用户那条实验 | 采用 |
| --- | --- | --- | --- |
| 总速度 | `outputTokens / (finishedAt − startedAt)` | **229.8 tok/s** | ✅ 界面唯一显示的速度 |
| 首正文延迟 | `firstTextAt − startedAt` | **168.3 秒** | ✅ 另外单独显示（推理模型的主要等待） |
| ~~错口径~~ | ~~`outputTokens / (finishedAt − firstTextAt)`~~ | ~~3703 tok/s（失真）~~ | ❌ **界面绝不出现**，验收脚本专门断言它不出现 |

为什么会失真：推理型模型先把大量 reasoning token 吐完才出正文，
用户那条实验里"等首正文"就花了 168.3 秒，而正文只写了 11.1 秒 —— 拿后者当分母必然虚高。

`reasoningTokens` 实测为 `null`（服务端没上报）→ 按既有约定写**"未上报"，绝不写 0**（F18 / A18）。

**盲选指纹判定（用户要求判断的部分）**：

- token 数与速度**不像**上下文窗口那样与某个模型一一对应（换个题目数字全变），**不是强指纹**；
- 但两点仍然成立：① 它们与上下文窗口 / 档位清单同属"调用元数据"，同一块面板里一半遮一半露很怪；
  ② 盲选要的是"先看作品"，把 235.8 tok/s 摆出来会把对比变成跑分、反过来影响投票。
- 所以**按既有约定整块隐藏**并写明"揭晓后可见"（`blindSafeText()` / `identityWords()` 那套约定的延续）。

**顺带修掉一个真实泄露**：v0.3.0 的「展开配置」在盲选期间**仍然把 token 数写出来了**
（旧代码只遮了 provider / model / 指纹，用量那一块漏了）。是本轮新增的"错误口径不得出现 / 指纹不得出现"
这类**跨面板整体断言**才把它抓出来的 —— 单看那个面板自己的断言是绿的。

### 本轮实测发现并修掉的三个真缺陷（都不是用户提的，是验证过程中撞出来的）

1. **"隐藏配置身份"在已揭晓的实验上是个死开关**：揭晓不可逆，但按钮只翻转 `state.blind`，
   于是点了画面什么都没变、文案却翻成"显示配置身份"。
   现在新增唯一判定入口 `identityHidden()`（替换掉散落各处的 `state.blind && !state.revealed`），
   **揭晓后按钮直接隐藏**，并把"未揭晓"写成盲选类断言的**硬前置条件**。

2. **一份"看起来脱敏、其实全是明文"的交付截图**：用一条已揭晓的实验去拍盲选图，
   脚本点的按钮已经不存在了，却照样出了图。现在 `delivery-shots.mjs` 会**先检查状态**，
   不合格就抛错拒绝出图；已揭晓时如实跳过并在输出里写明（不伪造证据）。

3. **两个演练脚本会把"状态相关"当成"默认值"**：
   `m2-ui-walkthrough` 断言"外部能力默认关"（开关是持久化的，上次演练开过就必然失败）、
   `m1-compare-walkthrough` 拿"轮次行数"要求"候选数"（追加过一轮的实验有 3–4 行）。
   都改成相对当前状态的断言，并把"默认关"交给 `m2-capability-walkthrough` 用"真关掉再试"的路径证明。

4. **指纹断言用朴素 `includes` 会误报**（本轮第二次跑到交付实例上才发现）：
   某条真实实验的输出 token 数是 **81**，而页面上到处是时间戳与耗时 ——
   `"81"` 作为**更长数字的一部分**偶然命中，报了一次"盲选泄露指纹"的假警。
   现在抽成 `fingerprintHit()`：**纯数字要求两侧都不是数字**才算命中，
   带字母/符号的指纹（模型 id、档位清单 `off / low / high / max`）照常 substring。
   `m2-usage-metrics-check` 与 `m2-four-walkthrough` 两处都已改用同一个函数。

5. **两个脚本并行跑会互相污染**：`m2-ui-walkthrough` 每次都重新 `fetch` 服务端设置去比对自己
   页面上的可见性，而另一个脚本正好在这中间改了开关 —— 页面还没重新加载，于是报假失败。
   改成**断言"界面可见性 == 这个页面自己依据的 (探测到 且 已启用)"**，不再跨进程读服务端。

### 反馈 1：手机逻辑视口下作品右边一条空白

**复现与根因**（真实 Chromium 量尺寸，不是看截图猜）：

| 状态 | 卡片宽 | 作品渲染宽 | 右侧空白 | 缩放 |
| --- | --- | --- | --- | --- |
| 修复前 · 手机视口 | 488px | 390px | **98px** | 1（卡住不动） |
| 修复前 · 1600px 窗口 + 手机视口（1.6× 上限版） | 742px | 624px | **118px** | 1.6（被上限截断） |
| **修复后 · 1024px 窗口 + 手机视口** | 486px | **486px** | **0** | 1.246 |
| **修复后 · 1600px 窗口 + 手机视口** | 742px | **742px** | **0** | 1.903 |
| **修复后 · 880px 窗口 + 手机视口** | 414px | **414px** | **0** | 1.062 |

根因是缩放公式里的 `min 1`：

```js
scale = Math.min(1, avail / vp.width)   // ← 错
```

手机逻辑视口只有 **390px**，而卡片通常有 400–490px。`min 1` 意味着**永远不放大** ——
作品就按 390px 原尺寸画出来，右边剩下的宽度全空着。

**修法**：抽出**唯一口径** `frameScale(vpWidth, avail, wide)`，`buildFrame()` 与
`refitFrames()` 共用它。**这一点比修复本身更重要** —— 那两处以前**各写了一份同样的公式**，
正是"同一份逻辑抄两遍"导致漂移出这个缺陷（与 M1 那次 dev-server 漂移是**同一类错误**）。规则：

- 「1:1 横向展开」且内容比容器宽 → 保持 **1:1**，横向滚动交给容器；
- **其余情况 → 等比缩放正好撑满容器宽度**，不留一点空白。

**一次被实测否掉的"想当然"**：我先给放大加了 1.6× 上限（怕插值糊），
结果**在 1600px 窗口下空白又以 118px 回来了** —— 那等于把缺陷挪到别的分辨率上。
最终**去掉上限**，让"撑满"成为**没有例外的规则**；看原始尺寸是「1:1 横向展开」的职责。
界面上同时写出当前倍数（"正好撑满、不留空白（当前 1.9×，390px 逻辑视口）"），
避免用户把放大后的画面误当成真实像素尺寸。

### 1. 配方快照与版本（A03 补齐）

### 2. 宿主重启恢复（A09，真的杀进程）

`node scripts/m2-restart-recovery-check.mjs` **23/23**。做法：起一个开发服务器子进程跑两个候选，
在"一个已完成、一个正在流式输出"时 **SIGKILL**，用同一个数据目录重启，然后核对状态与调用数。

**本轮实测暴露并修掉的一个真缺陷**：`markInterrupted` 原先只写在宿主半边（`src/index.js`），
开发服务器没有 —— 于是"重启后未完成仍标 running"在**零费用的开发服务器上根本复现不出来**。
现在抽成 `core/runtime.js` 的 `recoverUnfinishedAttempts()`，两边共用
（与 M1 那次"实时流缓冲只有宿主半边有"是**同一类错误，第二次踩**）。

**另一件必须补的事**：宿主被硬杀时，内存里的实时缓冲会一起消失，而 `raw.txt` 要等流结束才写 ——
原先"生成到一半被杀"留下的是一条**没有任何正文**的记录，可界面上却写着"已保留内容"（假信息）。
现在生成过程中每 1.5 秒把已收到的正文刷到 `partial` 文件（上限 256KB），跑完就删，
`raw.txt` 仍是唯一权威正文；界面多一个"下载中断前的部分输出（N 字符）"按钮。

### 3. 超时与取消（A08 补齐）

`outputPolicy.timeoutMs` 以前**只是存下来了**，从没有人用它中止调用。现在按本轮上限计时、到点尽力 abort，
并记成 `timed_out`；**超时与取消分开记录**；到点但流未收尾时 `/live` 报 `timedOut: true`，
界面写"已到运行上限，正在尽力中止…"。

"不污染新 attempt"用的是可核对口径（不是"看起来没串台"）：同批放一个**忽略中止信号**的候选，
正常候选 0 处沾到迟到内容；窗口内新开的那一轮正文长度**等于一次完整输出**，
且它的正文/作品 hash 都能从磁盘内容重新算出来。

**界面缺口（由 A08 的断言抓出来）**：超时的作品也可能有 HTML，原先对比页只显示作品、
完全看不出它超时了。现在卡片头对**非 completed**的候选加状态标记（超时/取消/中断/失败），
"展开配置"里补上"本轮状态 / 收尾原因 / 失败原因 / 上游原始错误 / 部分输出"。

### 4. 截图失败的正式记录（A23 补齐）

新增截图记录表，成功与失败都落一条（视口/状态/原因/耗时/页面诊断计数），**只记状态与原因，不记图片**。

现在在整个实验的尝试里找，标成"候选名 · 第 N 轮"。

### 九·2 关键设计：口径只有一份

### 九·5 两条流程教训

1. **改名是机械替换，它分不清"现在的名字"与"历史产物当时叫什么"。**
   `m4-upgrade-uninstall-check` 装的是 v0.4.0 / v0.5.0 的**历史包**
   （包名 `@dsh-external/html-arena`、前缀 `/html-arena`），
   替换把断言也改成了新名字 → **不可能成立的期望** → 5/7 假红，长得跟产品缺陷一模一样。
   **判据：遇到老版本产物，名字要从那个产物自己读出来（`vintageOf()`），不能在源码里写死。**
2. **"验收通过"要指得出用户真的点得到那一步。**
   A12 记着"通过"，证据只有单测 + 服务端接口，而界面上没有那个控件 ——
   接口做得到 ≠ 用户做得到。补齐后应记的是"补上了原先缺失的那一半"，不是把未测改写成通过。
